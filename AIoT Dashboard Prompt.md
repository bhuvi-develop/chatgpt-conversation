The single place any maintenance record is generated is `maintenance_service.py:384`, which hard-codes `MaintenanceType.PREDICTIVE`. ### Finding 2 — Predictive maintenance has never produced a single output

The module is real (438 lines, evidence-tagged trend analysis, honest docstring stating no model is trained). It has produced **0 rows**. Cause is data volume, not logic: it needs ≥9 trend points (`predictive.py:104`) and ≥12 runtime samples (`:290`) inside a 24 h lookback, and the database holds **15 hourly buckets total across all assets**. `ml-models/` contains only `.gitkeep`. `ml_models` table: 0. `classification_results`: 0. `/health` on the ML service reports `model_available: false`. No `sklearn`/`torch`/`xgboost` import exists in the backend at all.

## Two-source convergence

**The architecture is correct and better than your diagram requires.** Both paths share validation, storage, live-publish *and* the consent gate — the HTTP handler's docstring records a fixed bug where it used to bypass the gate and write rows with no `ingest_source`, which were "invisible on the dashboard tiles, but counted in every rollup, health score and OEE period."

Separation is enforced structurally, not by convention: `source` is part of the **primary key** of `telemetry_rollup_1h`, so simulated and measured data are physically incapable of merging into one bucket. The engine resolves one source per insight and refuses to blend.

## Secondary findings

**5 — README contradicts the code on OEE Quality.** `README.md:536` states Quality "is not derivable… null until supplied". In fact `analytics/oee/quality.py` (308 lines, 21 tests) computes `Quality = good windows / assessed windows`, and `oee_service.py:18` imports it. The doc is stale; the capability shipped.

**6 — Feature contract is duplicated with no cross-boundary test.** `FEATURE_ORDER` is defined twice — `backend/app/ml/features.py:21` and `ml-service/app/features.py:16` — with a comment saying they "must stay identical". **7 — \~1,356 lines of maintenance logic with no direct test.** `test_aiot_engine.py` imports only `analyse`, `build_feature_vector`, `detect_anomalies`. ## What is genuinely strong

Tenant isolation is structural (tenant in MQTT topic → broker ACL can scope a device credential). The ingest consent gate — brokers start paused, consent per-broker and per-device-uid, persisted in JSONB rather than Redis because Redis runs `appendonly no` with LRU eviction here — is unusually careful design. Provenance is carried row-level and into the rollup key. The wire format lives in one profile file read by both training and serving. **303 tests pass.**

## Ranked recommendations

1. **Implement preventive maintenance** or drop it from the capability list — it is the only one of six with no code.
2. **Run the pipeline long enough to prove predictive fires** — it needs \~24 h of continuous telemetry on one asset. Until then that capability is unverified.
3. **Mechanically enforce the feature contract** across the backend/ml-service boundary.
4. **Exercise the live path against real hardware** — the code and tests are ready; the deployment has never done it.
5. **Correct the README on OEE Quality** — it understates what you shipped.
6. Add direct tests for predictive and prescriptive.

One caveat on the row counts: they reflect this development database after a few hours of simulator traffic, not a production history. The *zeros* are the meaningful signal — particularly `maintenance_predictions: 0` and the absence of any non-`local` source.
